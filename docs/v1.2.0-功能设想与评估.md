> 定位：这是**评估与建议**文档，不含实现代码。基准版本 v1.1.0（`versionCode 1000100`）。
> 输入：《##鹿了么 v1.2.0 升级计划.md》提出的 3 个 Bug + 2 个新功能。
> 结论口径：能落地到本仓库现有代码与 HarmonyOS API 24 的，写成"怎么做"；做不到或有合规风险的，直接说不行。

## 一、对计划里 5 项的技术判断

### 1. 左右滑动切页"动画突兀" —— 根因很可能不是缺动画，而是动画叠了两层

现状（`entry/src/main/ets/pages/Index.ets`）：

| 位置 | 行为 |
|---|---|
| `:289-291` | 切页前先把 `contentAlpha = 0.86`、`contentOffsetY = 6` |
| `:298-303` | 再 `animateTo({ duration: 220, curve: FastOutSlowIn })` 把两者拉回 `1 / 0` |
| `:590-591/:607-608/:618-619` | 三个页面根容器都挂 `.opacity(this.contentAlpha).translate({ y: this.contentOffsetY })` |
| `:629` | `.cachedMaxCount(3, TabsCacheMode.CACHE_BOTH_SIDE)` 页面驻留 |

这套"淡入 + 纵向轻浮"是**为点击切换设计的**（掩盖数据刷新延迟）。但手势左右滑动时，HdsTabs 自己会做横向位移动画，此时页面又同时在做"透明度 0.86→1 + 上浮 6vp"，两个位移方向正交、两条时间曲线不同步，观感就是"抖一下 / 弹一下"。

修复方向（做减法）：

- 区分来源：`onSelected` 里判断是否由手势触发，**手势滑动不加 opacity/translate**，让 HdsTabs 自带的横向动画独占；
- 点击切换保留淡入，但把纵向位移去掉（横向轨道的 Tabs 里做纵向位移本身语义就不对），只留 opacity 或只留极短的位移；
- 顺带检查是否覆盖了 HdsTabs 的 `slideAnimation` / `barOverlap` 之类的默认参数。

> 判断依据是代码结构，不是"猜"；但需在真机上对比"手势 vs 点击"各录一帧确认。

### 2. 导出 JSON 后缀显示不正确 —— 大概率是"后缀写了两遍"

`entry/src/main/ets/pages/Settings.ets:165-201` `exportBackup()`：

```ts
const uris: string[] = await documentPicker.save({
  newFileNames: ['luleme_backup.json'],   // :174 名字里已经带 .json
  fileSuffixChoices: ['json']             // :175 又声明了一次后缀
});
```

`@ohos.file.picker.d.ts:595` 对 `fileSuffixChoices` 的说明是"保存文档的后缀选项"，元素支持 `描述|后缀` 形式；而 `newFileNames` 是"建议文件名"。两者同时给后缀，不同系统版本/文件管理器的处理并不一致 —— 可能变成 `luleme_backup.json.json`，也可能被截断成 `luleme_backup`（后缀被吃掉），恰好对应"有时显示不正确"。

修法二选一（不要双写）：

- A：`newFileNames: ['luleme_backup_20261030-2312']` + `fileSuffixChoices: ['备份文件|json']`，让系统补后缀；
- B：`newFileNames: ['luleme_backup_20261030-2312.json']`，不传 `fileSuffixChoices`。

并且保存后用返回的 `uris[0]` 校验结尾是否是 `.json`，不是则提示或补写。

### 3. 导出文件名加时间戳 —— 建议这么做

`luleme_backup_20261030-2312.json`

- 时间戳用 `YYYYMMDD-HHmm`，**不要冒号和空格**（跨文件系统/网盘同步最容易出问题）；
- 用"年-月-日 时-分"而不是秒，避免用户在同一分钟内导出两次时覆盖（若要绝对安全可加两位随机）；
- **文件名保持英文 `luleme_backup`，不要写成"鹿了么记录备份"**：这个文件会落到 `Download` / 用户选的网盘目录，中文名+应用名等于在文件系统里自曝内容性质。这一点比"命名好看"重要。

### 4. 定时提醒 —— 用 reminderAgentManager，不要自己保活

已核实 `@ohos.reminderAgentManager.d.ts`：

| 能力 | 签名/字段 |
|---|---|
| 发布 | `publishReminder(reminderReq: ReminderRequest): Promise<number>` |
| 取消 | `cancelReminder(reminderId: number): Promise<void>` |
| 查询 | `getValidReminders(): Promise<Array<ReminderRequest>>` |
| 周期 | `ReminderRequestCalendar.repeatMonths / daysOfWeek`；`ReminderRequestAlarm.daysOfWeek` |
| 稍后提醒 | `snoozeTimes`、`expiredContent` |

优点：系统级调度、**重启后依然有效**（不需要开机广播）、用户能在系统里统一管理、可以做"稍后提醒"。

代价与注意：

- 需要声明 `ohos.permission.PUBLISH_AGENT_REMINDER`（现有 `entry/src/main/module.json5` 只声明了 `ohos.permission.ACCESS_BIOMETRIC`）；
- 提醒是**系统提醒**，不是普通通知，文案会显示在锁屏/通知中心 —— 这对本应用是隐私风险点，见下文"隐私"；
- 首次发布可能触发授权弹窗，需要在 UI 上给出"提醒未开启"的兜底提示。

明确不推荐：`continuousTask` 后台常驻、`WorkScheduler` 轮询。前者耗电且上架审核敏感，后者最小粒度 20 分钟且会被系统合并延迟，都得不到"准点闹钟"的效果，纯属增加复杂度。

### 5. 「葛神模式」每 8 小时提醒 —— 建议改成"记录后 8 小时"

单纯的"每 8 小时整点提醒"（0/8/16 点）机械且容易变成骚扰。更贴合产品调性的形态是**绑定行为**：

- 用户每次记录后，`publishReminder` 一个 8 小时后的一次性提醒："距上次已经 8 小时了，想变得和葛神一样强大吗？"；
- 用户下次记录时，`cancelReminder` 旧的、重建新的 —— 提醒永远只指向"距上次"这个语义，天然不会累积；
- 叠加两道刹车：每天最多 1 次、可配置静默时段（如 23:00–08:00 不提醒）。

如果坚持"固定每 8 小时"，用 3 个 `ReminderRequestAlarm`（0/8/16 点，`daysOfWeek: [1..7]`）也能实现，但请务必给关闭开关和静默时段。

## 二、建议补充的功能（按优先级）

### P0 — 与 v1.2.0 主题（提醒 + 隐私）直接相关，建议同批做

1. **窗口隐私模式**：`@ohos.window.d.ts:6873` `setWindowPrivacyMode(isPrivacyMode: boolean): Promise<void>`（since 9）。开启后截屏、录屏、任务切换缩略图都变黑/遮罩。这是本应用最该有的开关，价值高于任何新功能。建议：默认开启，设置页提供关闭（方便用户自己截图反馈问题）。
2. **通知/提醒内容脱敏**：提醒文案默认中性化（"该记录一下啦"），"是时候鹿了！"这类文案作为**可选项**并明确提示"将显示在锁屏上"。
3. **自动锁超时可配置**：现在有 PIN 锁，但没有"退到后台多久后重新验证"。建议 立即 / 30 秒 / 1 分钟 / 5 分钟。
4. **删除可撤销**：现在删除是"确认对话框 + 直接删"，误删无法恢复。改成删除后 Toast 支持 3 秒内撤销（软删除或内存暂存后延迟落库）。
5. **备份加密**：`entry/src/main/ets/logic/SecurityUtil.ets` 已有加密能力，`exportBackup()` 导出的却是**明文 JSON**。建议加"导出时设置口令 → AES-GCM 加密"，`importBackup()` 识别加密与明文两种格式。

### P1 — 体验与洞察，成本低、感知强

6. 快捷记一笔：长按"＋ 记一笔"直接用上次的心情/备注，一键落库。
7. 记录页"保存并继续"：连续补记多天时不用反复进出。
8. 日期/时间选择默认上次使用值，而不是"此刻"。
9. 备注常用语（本地模板，如"晨间/睡前/独自"），减少输入摩擦。
10. 时段分布（24 小时热力）与星期分布，比"趋势图"更能让人看见自己的节律。
11. **连续记录天数** 与"近 7 天次数/目标进度"：现在统计页只有总次数/最长间隔/平均间隔/距上次，缺少"我在坚持吗"的反馈。
12. 里程碑（首次记录、连续 7/30 天、累计 100 次），但用"记录行为"而非纯次数，避免鼓励高频。
13. 年度回顾（本地生成的一页总结，可导出图片但默认不含敏感内容）。
14. 空态与引导优化：首次进入给一句"为什么记录"的说明，而不是直接摊开日历。

### P2 — 平台与可达性（上架加分项）

15. 桌面服务卡片（`@ohos.app.form.*` 已存在）：显示"今日 N 次 / 距上次 X 小时"，并提供一键记一笔。注意卡片内容也要脱敏。
16. 大字体/无障碍：给图标按钮补 `accessibilityText`，检查 `fontSize` 是否用了 `fp`（随系统字体缩放）。
17. 折叠屏/平板：`module.json5` 的 `deviceTypes` 现在只有 `phone`。
18. 多语言：文案目前全中文硬编码在 `resources/base`，若要出海需抽到 `resources/en_US`。
19. 冷启动：`EntryAbility` 初始化 + 首页读库可并行化（当前是串行 await）。

### P3 — 工程与合规

20. DB schema 版本化迁移（现在 `RecordRepository` 建表逻辑是幂等 `CREATE TABLE IF NOT EXISTS`，加字段时会缺列）。
21. 备份格式版本校验：导入时校验 `payload.version` 与 `app`，不匹配给出明确提示而不是静默失败。
22. 本地崩溃日志（写入应用沙箱，不上传），便于用户反馈问题时导出。
23. 隐私政策 / 用户协议页（应用商店上架必需，尤其"性健康"类目）。
24. 商店文案中性化：应用名"鹿了么"、描述、截图都要规避露骨表述，否则国内应用市场容易被拒。
25. 单测扩充：`entry/src/main/ets/logic/StatsCalculator.ets` 是纯函数，适合补边界用例（跨月、跨年、空数据、时间戳为 0）。

## 三、明确不建议做的

| 想法 | 为什么不建议 |
|---|---|
| 云端同步 / 账号体系 | 与"数据仅存本机"的核心卖点冲突；若一定要做，必须端到端加密 + 默认关闭 + 隐私政策重写 |
| 社交、分享、排行榜 | 隐私伤害不可控，且与产品调性不符 |
| 后台常驻保活、开机自启 | 耗电、审核敏感，且 reminderAgent 已经能跨重启 |
| 抽卡/成就等级等强成瘾设计 | 伦理问题，也会放大"高频"导向 |
| 接入第三方统计/广告 SDK | 隐私政策负担陡增，与"仅本机"叙事矛盾 |

## 五、需要你拍板的三个问题

1. 「葛神模式」要"固定每 8 小时"还是"记录后 8 小时"？我推荐后者（更聪明、不会积累骚扰）。
2. 提醒文案是否允许出现在锁屏？这决定默认文案的敏感度，以及是否强制与"隐私模式"绑定。
3. 导出文件名要不要带中文？我建议不带（`luleme_backup_YYYYMMDD-HHmm.json`），理由是文件会离开应用沙箱。
